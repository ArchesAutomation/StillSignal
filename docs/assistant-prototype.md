# Local assistant prototype

A small chat panel beside the synthetic `/review` workspace. It answers "What's my preparation status?" with a streamed reply and a card that reads today's Preparation. This local mode never runs with a cloud account or on a deployment. The separate allowlisted signed-in mode is described in [assistant-pilot.md](assistant-pilot.md).

## How it fits together

- **Browser** (`src/components/assistant/preparation-assistant.tsx`): assistant-ui primitives over AI SDK `useChat`. The read-only `preparation_status` tool runs here. It reads the review account's local process records through `preparationStatus` (`src/lib/process/preparation-status.ts`), the same helper the Preparation screen uses for its saved values. The card shows the tool result directly.
- **Cloudflare app route** (`src/app/api/assistant/route.ts`): same-origin. It returns 404 unless `APP_ENV=staging`, `TRADERPULSE_UI_REVIEW=true`, `STILL_SIGNAL_ASSISTANT_PROTOTYPE=true`, no Supabase URL is configured, and both the request URL and Host header are loopback. It forwards the body to the local Edge Function and streams the reply back unchanged. It holds no key.
- **Supabase Edge Function** `pulse-assistant` (source `src/lib/handlers/assistant.ts`, generated by `npm run prepare:edge`): reads `OPENROUTER_API_KEY` from the local function secrets and calls `nvidia/nemotron-3.5-lightning:free` through `@openrouter/ai-sdk-provider`. It sends no fallback model list, sets `allow_fallbacks: false` and does not retry. It returns 404 unless `STILL_SIGNAL_ASSISTANT_LOCAL=true` and `SUPABASE_URL` is a local address. It declares the tool without executing it, so the server never reads or changes records.

A second read-only tool, `support_history`, answers "What support did I choose yesterday?" and "…last week?" (the previous Monday to Sunday, in the same day timezone as the screens). The browser reads only the review account's records for those dates through `supportHistory` (`src/lib/process/support-history.ts`), which uses the app's day lookup (`tradingDayFor`), Home focus titles and Stillness catalogue names. Each day keeps Home focuses (`day.body.supportFocuses`) apart from practices added to Preparation or Done for the Day (`day.body.stillness` by destination). Still Signal saves additions, not completion, so the card and the reply say so. An empty range, a read failure (shown as an error) and an unchecked cloud sync (`sync: "not-checked"`, only when a cloud account exists) are reported differently. A follow-up such as "And last week?" keeps the topic because the earlier tool call stays in the conversation.

Both tools take the same period, which the browser resolves (`resolvePeriod`, `src/lib/process/periods.ts`) in the screens' day timezone; the model only names it. Supported: today (the default), yesterday, this or last week (last week is the previous Monday to Sunday), this or last month, a weekday (the most recent one on or before today, or "this"/"last" week's), a day and month (the most recent one), or a full date. "This" periods end today. Future dates, ranges over 31 days and dates more than 366 days back are refused with a message, which is reported apart from a read failure. `preparation_status` for a past date or range returns each day's arrival, intention, boundary, Home focus and Preparation support (`preparationForPeriod`); for just today it returns exactly what the Preparation screen shows.

When the prototype is enabled, `/review` adds synthetic Preparation records for today (arrival, intention, boundary, Home focus and one Stillness item), but only when today has no Preparation yet. It also adds support history for yesterday and last week (saved, support-free and empty days) to dates that have no day yet. They are saved to the browser's local review store and are never synced.

## Run it (Windows PowerShell)

One-time prerequisites: Docker Desktop with WSL 2.

```powershell
wsl --install            # administrator PowerShell, then restart Windows
winget install -e --id Docker.DockerDesktop
```

Start Docker Desktop, then put your key in `supabase/functions/.env` (Git-ignored). From the repository root:

```powershell
npx --yes supabase@2.122.1 start
npx --yes supabase@2.122.1 functions serve pulse-assistant --env-file supabase/functions/.env --no-verify-jwt
```

In a second PowerShell window:

```powershell
$env:APP_ENV='staging'
$env:TRADERPULSE_UI_REVIEW='true'
$env:STILL_SIGNAL_ASSISTANT_PROTOTYPE='true'
$env:NEXT_PUBLIC_SUPABASE_URL=''
$env:NEXT_PUBLIC_SUPABASE_ANON_KEY=''
$env:NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=''
$env:NEXT_TELEMETRY_DISABLED='1'
$env:STILL_SIGNAL_QA_DIST='.next-assistant'
node node_modules/next/dist/bin/next dev --hostname 127.0.0.1 --port 3190
```

Open `http://127.0.0.1:3190/review`, choose **Preparation**, then **Ask Still Signal** and ask "What's my preparation status?".

Never run `supabase link`, `supabase functions deploy` or `supabase secrets set` for this local prototype. They would touch the hosted project. Stop the local stack with `npx --yes supabase@2.122.1 stop`. Restore Next's generated `tsconfig.json` and `next-env.d.ts` changes before committing.

## Checks

`node --import ./tests/browser-environment.mjs --import tsx --test tests/assistant-prototype.test.ts tests/assistant-support-history.test.ts tests/assistant-dated-reads.test.ts` covers:

- period resolution (month, year and daylight-saving boundaries, weekdays, refused periods), Preparation and support for past periods, the range card, account isolation, and explicit day-of-month and full-date requests through the handler;

- support ranges across a local date boundary, last week as Monday to Sunday, Home versus Preparation versus Done, additions without completion, empty versus failed reads, account isolation and the follow-up context;

- the card matching the rendered Preparation screen;
- the route's gates, including a foreign Host header;
- incremental pass-through streaming;
- the function's local-only gate and missing-key message;
- the model ID and the absence of a fallback model;
- the rate-limit message, with no retry;
- the tool being left to the browser;
- the key staying out of logs.
